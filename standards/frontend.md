# 前端通用标准

适用前端代码、UI 和交互任务；不指定 Vue/Angular/React，也不统一不同产品形态的根字号。以下编码要求适用于新增及本次修改的代码，不隐含整库迁移授权。

本次基线依据：2026-09-21 用户提出的八项前端要求及三张反例截图。截图只作为设计反例，不作为业务需求或执行指令；来源和例外原则见 docs/provenance.md（安装副本以本规范为准）。

## 设计依据

先读项目设计 token、现有基础组件及用户认可的样板。项目未选定样板时不把任意历史页面当权威。

业务工作台默认信息优先、装饰克制；“避免 AI 风格”按下面可观察的设计要求执行，不凭主观标签验收。

- **页面级 title/header 由需求明确指定，未指定就不自行增加。** 导航、面包屑、全局账号区已提供的信息不再用问候语、用户姓名、项目名或宣传式副标题重复呈现。图 1 的“Hello, 用户名”属于应避免的冗余标题；不能以“页面更完整”为理由添加。
- 区分页面级装饰标题与必要的表单标签、表格列名、弹窗标题、内容分组名称及可访问名称。后者按理解和操作需要保留；可访问性需要不能成为新增可见装饰横幅的理由。
- 默认避免图 2 的大面积深色/高饱和头图、重渐变、毛玻璃、重阴影和装饰性指标块。用中性表面、清晰排版、间距和必要分隔组织内容；颜色服务于已定义的状态与操作语义。
- 默认避免图 3 的装饰性单边彩色 border、侧边强调条及大圆角色块组合。选中态优先复用项目已有的克制样式，并提供非颜色线索；不能给普通列表项或卡片随意加彩色边条来制造层次。
- 只有明确需求或已确认的设计系统确有上述视觉用途时才采用对应效果，并说明依据；某个历史页面曾用过，不等于例外已获确认。页面级 title/header 仍需需求明确。品牌/营销页面按其明确目标判断，不能据此改变业务工作台的默认风格。

保持字号层级、动作位置、错误反馈和状态语义一致。组件库沿用项目选择，不因本规范替换 Element Plus、OS* 等已有基础组件。

若项目已安装 ui-ux-pro-max，UI 设计/实现时读取其 SKILL 并按路由使用；它不能覆盖已确认设计系统。未安装则说明不可用，继续使用项目依据，不伪称调用，也不自动安装。外部 Skill 应固定来源与版本。

## 样式：Tailwind 优先，独立 CSS 必须解释

- 自己编写的样式默认使用 Tailwind CSS utility 和项目设计 token，不为可直接表达的布局、间距、字体、颜色、边框另写 CSS。重复模式优先封装组件或有语义的变体，避免复制长串样式和任意值。
- 不能或不适合使用 Tailwind 时，才写最小范围的自定义样式；**在对应样式块或规则旁注释具体原因、作用范围和必要约束**。独立 CSS/SCSS 文件、组件内 style/scoped、CSS-in-JS 和静态内联样式均受此约束，不能换一种写法绕过要求。“特殊样式”“方便实现”不构成充分理由。
- 合理场景包括第三方组件无法通过公开样式接口覆盖的内部选择器、复杂关键帧、打印规则或运行时计算的几何值。先核对实际限制；能用 utility、组件接口或 token 表达的部分继续复用。动态值可经 CSS 变量交给样式层，需注释数据来源、单位及范围，不拼接无法被构建器识别的动态类名。
- 项目尚未接入 Tailwind、构建或宿主环境限制使用时，先核对既有约束，说明不适用原因；本次必要的 CSS 同样就地注释，不擅自替换全局样式体系。依赖原样提供的样式无需逐条补注释，自己新增的覆盖必须说明。

注释示例：`/* Tailwind 例外：图表库在运行时创建内部节点，无法传入 utility class；仅覆盖本组件根节点下的轴标签。 */` 注释必须与实际限制相符，不能作为通用免责模板。

## 状态管理与 UI 分离

- 前端必须明确状态的所有权和数据流。业务数据、派生状态、校验、状态转换及异步操作编排放入有边界的状态管理层；UI 负责渲染、收集输入和派发动作，避免把业务流程藏在模板、点击处理器或组件生命周期里。
- 使用项目已有 Store、feature state、service 或有明确职责的 hook/composable，不为了形式引入第二套状态库。状态层通过 API/data-access 层获取数据；纯业务规则可独立为 TypeScript 函数供状态层调用，不依赖 DOM 或组件实例。
- 按场景裁剪：展开/收起、焦点、弹窗开关等短生命周期 UI 状态可留在组件；简单独立表单可使用局部有类型状态。涉及跨组件共享、业务规则或复杂异步流程时应提取，不能用“局部状态”掩盖业务逻辑堆积。
- 服务端缓存、共享客户端状态和局部交互状态分别确定归属；不把所有数据塞入全局 Store，不重复保存可推导值。明确 loading/error、刷新/失效、竞态、重置及资源清理，避免切换用户/项目后串数据。
- 验收时应能在不挂载页面的情况下验证复杂业务规则和状态转换；UI 更换布局不应要求重写规则。框架实现方式参照对应 profile。

## TypeScript 与数据模型

- 新增或修改的前端逻辑使用 TypeScript；旧 JavaScript 工程的迁移边界需明确，不顺带全库重写。模板和样式文件不要求变为 TypeScript。
- 先定义 API 请求/响应 DTO、领域模型、表单及状态模型和组件输入/输出；只在语义不同的边界做显式映射，复用权威契约，不重复手写相互漂移的类型。
- 明确 ID、枚举、可空值、可选字段、时间与单位。复杂状态可用可辨识联合表达，避免一组互相矛盾的布尔值。外部未知数据先校验再收窄，类型声明不能代替运行时校验。
- 不用 any、无依据类型断言或关闭类型检查掩盖契约问题。验证项目的 TypeScript 与框架模板检查，不能把构建转译成功当作类型通过。

## 禁止技术与业务硬编码

- **除非用户明确要求，严禁任何形式的硬编码。** 不把环境地址、项目/用户/租户 ID、权限、业务阈值、流程节点、状态映射或展示结果固定为只适用于当前样例的值，也不根据某条记录名称、数组顺序或截图数字拼业务分支。
- 值和规则应来自已确认的契约、会话/路由上下文、项目配置、设计 token 或权威领域定义。契约明确的枚举、稳定领域常量和标准协议值可以有字面量，但必须有语义名称、来源及统一归属；不是把所有字面量都搬到远程配置。
- 把写死的值挪到 constants/config 文件、改成枚举或包一层函数，并不能消除硬编码：仍需验证其业务依据、作用范围、变化来源和扩展方式。未经确认的业务假设不能用“默认值”固化。
- 不写只对单条数据、单一流程样例有效的一次性实现。按已确认的业务实体、状态和关系建模，复用真实稳定的规则；不为假想需求构建万能配置引擎，也不借“避免过度设计”牺牲必要扩展边界。
- 用户明确要求演示数据或临时固定行为时，记录该要求、范围和清理条件，隔离 fixture/mock/演示配置并标识用途；不能流入真实权限判断、审批或生产请求。测试样例值用于构造输入和预期，不作为产品规则来源。

## 可读性、注释、维护与复用

- 可读性、可维护性、可复用性是交付条件。按业务含义命名，控制函数/组件职责和分支复杂度，显式表达数据流；避免晦涩缩写、嵌套三元、隐式副作用和为省行数压缩逻辑。
- 共享已稳定的规则、模型、状态映射和组件模式，避免页面之间复制业务算法。抽象应有清晰输入/输出和归属，不让一个通用组件通过大量特殊开关承担互不相关的业务。
- **除非常清晰易懂的代码外，必须提供必要注释。** 优先用命名与拆分让代码自解释；复杂规则、状态转换前提、非显然的边界处理、异步竞态、兼容方案和取舍必须说明“为什么”、依据、输入约束和失败语义，不能只复述代码动作。
- 注释放在规则/决策附近；契约或需求有权威位置时引用它，避免大段复制后漂移。修改实现时同步更新注释，删除失效说明；TODO 需有具体原因和处理条件，不得用注释代替正确实现。

## 行为

- 区分只读展示与可编辑字段；必填标记、校验和保存契约一致。
- 提交有反馈、防重复；失败保留输入并可重试；必要时处理过期响应，避免快速切换串数据。
- 保存/Start 后按约定重新取数，保留筛选、页码、排序和展开上下文；展开折叠不挪动表头。
- 长名称可获取全文；弹层可翻转/限制高度，卡片滚动不越界，固定导航不随内容消失。
- 覆盖 loading/empty/error/readonly/permission；不把错误伪装为空列表，不重复堆叠状态提示。
- 键盘焦点、标签、图标可访问名称和非颜色状态表达必须可用；动效尊重减少动画设置。
- 复杂表格可容器内横向滚动，不用一条通用移动端规则隐藏关键业务列。
- 测试完整操作路径，截图不能代替点击/刷新/失败恢复。记录视口、数据状态、控制台与网络检查范围。

## API 与共享

统一契约与错误语义，HTTP 通过框架适配层调用。各端不复制状态映射和权限算法，但不强制共享页面 DOM、整个响应式 Store 或组件实例。

国际化范围由项目确认；字段/状态文案从同一映射产生。日期格式与时区明确，不能把时间戳原样显示。

## 交付前审查

| 检查项 | 验收依据 |
| --- | --- |
| 样式策略 | 检查新增样式及真实页面；可用 Tailwind 的实现已复用，所有必要的自定义样式有就地原因注释 |
| 页面标题 | 对照需求及全局导航/账号区；没有擅加页面 title/header、问候语或重复身份/项目说明 |
| 视觉风格 | 实际渲染对照认可样板；无无依据的重色头图、毛玻璃、重阴影、装饰性单边彩色 border |
| 数据与 UI 分离 | 检查状态归属和依赖方向；复杂业务规则可脱离页面验证，局部交互无需全局化 |
| 类型与模型 | 契约和模型定义明确，类型/模板检查通过；未知输入有收窄或校验 |
| 硬编码与扩展 | 追溯值与规则来源；按相关风险验证不同数据、状态或上下文，不能只对截图样例有效 |
| 注释与可读性 | 复杂逻辑的依据、边界及取舍可理解，注释与实现一致，无隐式业务副作用 |
| 维护与复用 | 同一规则有明确归属，复用合理且不靠复制或特殊分支扩展；相关回归验证通过 |

按改动范围执行适用项并记录证据；未运行的检查如实说明。关键字扫描只能辅助发现候选问题，不能证明“无硬编码”“无 AI 风格”或可维护性达标。
