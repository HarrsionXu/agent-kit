# 风险分级开发流程

本规范定义默认工作方式：职责完整、过程按风险裁剪、结果有证据。它不是模型调度程序，不会自行创建 Agent、ticket 或审批任务。

## 职责与执行方式

| 职责 | 必须关注的结果 | 不要求的形式 |
|---|---|---|
| product-analyst | 要解决的问题、范围、业务规则和可观察的验收 | 每个小修改都写独立 PRD |
| architect | 影响边界、既有模式、契约兼容和必要取舍 | 每次改动都写架构设计或引入新抽象 |
| engineer | 实现、必要测试、相关文档与错误处理 | 只输出代码，把验证全部留给下一轮 |
| qa-devops | 验收对照、回归证据、未验证风险和必要的发布说明 | 自动发布，或将同一 Agent 自查称为独立 QA |

一个 Agent 可以完成这些职责，实际执行可交错迭代；不强制逐个角色运行、固定 Step Plan 模板或每个角色结束后等待“继续”。只有当前工具与指令允许、且确有独立子任务时才考虑委派，不为模拟团队拆分任务。

## 按任务选择流程

先完整读取有效 AGENTS、任务相关规范与 Skills，检查项目现状，再决定风险和验收。不要先编写与项目事实脱节的 PRD/ticket。保留项目技术约束、安全限制和明确的审批门槛；Kit 不自动覆盖仍然有效的上层指令或项目例外。

| 类型 | 流程 | 停止点 |
|---|---|---|
| 咨询/审查/诊断 | 读证据、解释原因与取舍，必要时给修复建议 | 没有修改授权就交付结论，不实施修复 |
| 小 UI / 明确 bug | 验收样例或复现、最小修改、针对性检查、必要交互核验、交付 | 范围/契约冲突；否则一轮闭环 |
| 普通功能 | 轻量需求和验收、必要设计、小步实现与回归、交付 | 影响结果的关键业务语义未确定；否则连续推进 |
| 跨工程/认证/架构 | 影响与方案、关键决定、分批实现与验证 | 公共契约、架构或安全边界的变更尚未确认 |
| 数据迁移/部署 | 环境与目标核对、恢复计划、执行授权、执行后核验 | 外部变更缺少相应授权；只有“准备方案”时不执行 |

按影响、可逆性和不确定性判断风险，不按文件数量判断。跨两个工程的小型兼容修复不必机械暂停；一行鉴权变更也可能需要关键确认。已经明确确认的决定不因角色切换重复确认。

最小闭环：读取规则和项目上下文 → 明确验收 → 必要设计与拆分 → 实现和测试 → 行为/视觉核验 → 修正 → 证据交付。若条件不足，完成安全且有价值的部分，明确剩余缺口；不能把缩短流程当作免除验证。

## 什么时候暂停

需要暂停并提出具体问题的情况：

- 业务规则或方案存在会改变结果的歧义，无法从已有事实确认，例如角色权限、数据删除语义、接口字段契约。
- 必须改变未获确认的公共契约、核心架构或安全边界；先给依据、影响和建议，确认后再实施该部分。
- 下一步超出授权，例如从诊断转为修改，从本地实现转为发布、生产迁移、发送邮件或真实审批。先说明精确目标和外部影响。
- 用户明确要求先给方案、逐步确认、只执行某一步或暂停。
- 缺少必要权限、凭据或环境，安全的替代检查已不足以继续；说明已验证的事实和需要补充的条件，不反复重试同一失败。

角色切换、完成文档、测试出现可修复的本地失败，不是默认停止点。发现失败后，在已授权范围内修正并重验。低风险、可逆的细节可沿用项目惯例并说明假设，不为每个命名或样式选择追问用户。

“开始任务”按已明确的目标与权限开始本流程；“继续”从最近已验证的进度恢复当前任务，不隐含进入下一角色，也不扩大原授权。明确的“先分析/分步确认”要求优先于这里的连续执行默认值。遇到仍生效的旧流程冲突，说明来源并请求统一，不静默改写其他工程规则。

## 任务记录

小任务可在对话中记录，不强制生成 ticket、PRD 和架构文件。多轮、高风险、迁移任务使用业务工程内的持久化记录，或关联已有任务系统；模板见 [任务模板](../templates/task.md)。Kit 只保存公共规则和空白模板，不保存业务 ticket。

记录目标、非目标、路径/应用、验收、假设/决策、检查命令和结果；复杂任务补上依赖、当前状态和下一步。按可独立验收的业务结果拆 ticket，不按四个角色各建一张。已有 PRD/契约/任务系统应引用权威来源，不维护重复副本。中断后从已完成证据继续，不从头重复实施。

## 完成与交付

- 实现必须对照验收案例，包含相关异常路径；前端改动按风险验证真实交互与视觉，纯文档改动验证一致性与链接，不无端要求业务浏览器测试。
- 报告实际运行的命令、结果和证据；区分未运行、失败、通过。lint、类型检查、构建、单测、浏览器验证各自证明不同内容，不能互相冒充。
- 交付包含改动摘要、关键决定、证据、未验证项和必要后续。只有确有需求/契约/设计变化时更新对应文档，不为凑齐角色产物制造文档。
- 代码完成与发布完成分别报告。没有执行授权就交付发布建议，不自动发布；同一 Agent 的审查标为自查，独立审查必须来自实际独立执行。

## 升级标准

同类错误复发时判断是规则未读、规则错误、工具缺失还是测试缺口；选对应修复。先验证新规则再发布新版本，不自动让所有项目跟随 main。

公共规则与项目例外应记录原因和审核日期。不能把私有业务配置复制到公共包。新版本先在隔离 fixture 和一个获授权业务项目试用，再推广。
