# UI / UX 设计与验收

适用前端页面结构、视觉和交互任务，与 frontend 编码规范一起使用。依据：2026-09-22 用户确认保留 ui-ux-pro-max 作为按需参考，以项目基线、设计流程和真实验证约束交付。默认使用项目代码与浏览器制作原型，暂不引入专业设计工具；后续明确采用其他工具时可调整，不将工具选择变成永久限制。

## 规则与参考的关系

- 项目基线记录已确认的产品形态、组件、token 和页面模式；不能由检索结果或任意历史页面自动替换。用户当前要求优先；涉及未确定的业务、安全或公共契约时按 workflow 处理。
- ui-ux-pro-max 等外部 Skill 保留为可选参考，不再要求每个 UI 任务读取或检索。只有项目依据不能解决具体问题（如表单错误定位、弹窗焦点、图表表达），或用户明确指定时才使用；使用前读取 SKILL，按需检索并检查适用场景。没有安装不自动安装，不伪称调用。
- 存量工程新增页面先复用现有设计系统，不因外部 Skill 的“新页面生成设计系统”步骤重新选择字体、主题或组件库。确需新设计方向时，输出仍是候选方案，不能直接设为已确认基线。
- 对建议检查产品形态、用户任务、技术栈和项目约束。业务工作台检索出 Hero、宣传卖点、联系销售、客户 Logo 等营销结构时拒绝套用；与任务无关的建议无需继续搜索凑结果。记录实际采纳的建议、必要的冲突取舍和验证范围。
- 外部 Skill 固定来源与版本或提交标识。读取、执行检索、采纳建议、通过验收是不同事实，交付不得混用。Skill 不能代替业务需求、用户研究或浏览器验收。

## 项目设计基线

在业务工程既有设计文档中维护唯一基线；没有时参考随 Kit 分发的 `templates/design-baseline.md`，填写项目自有文档，并把入口登记到项目事实或适用的 AGENTS。不要把填写后的业务内容写回中央模板或受管理副本。多端产品分别标明适用范围，不用一套字号/密度覆盖全部端。

基线至少明确：

1. 用户、核心任务、使用设备及信息密度；哪些行为与业务规则已经确认，哪些尚待确认。
2. token 和组件的权威路径、适用端、使用约定。引用现有定义，不复制另一份颜色或字号数值表。
3. 列表、详情、编辑等页面模式：信息分组、主要动作、筛选与导航、表单/弹窗/抽屉选择依据。
4. 样板路径或路由、认可的部分、不应沿用的部分、参考截图的视口/数据状态、确认依据与日期。
5. 交互状态、验证命令/操作路径、已知例外及复查条件。

存量项目从已获认可的页面提炼。没有认可记录的页面只能标为候选；可以复用权威组件继续做原型，不编造认可状态。新工程先选择代表性业务页面形成候选基线，确认后复用。未定样板不阻碍已有基线内的小修改，也不需要为每个任务重新确认全部设计。

## UI 和 UX 的可观察要求

视觉、标题、Tailwind、模型与状态边界遵循 frontend；下面补充设计决策及验收，不重复维护 token。

| 关注点 | 设计要求 | 验收方式 |
| --- | --- | --- |
| 信息结构 | 内容按用户任务分组，同一上下文有主要展示位置，主操作优先级清楚 | 用真实任务说明用户先看什么、下一步做什么；检查重复信息与无业务用途区块 |
| 页面模式 | 列表便于查找比较，详情便于理解追溯，编辑区分只读和可编辑内容 | 对照认可样板和操作任务；不能只凭视觉相似认定业务一致 |
| 表单反馈 | 必填与约束明确，错误可定位，提交防重复，失败保留输入 | 实测无效输入、提交中、失败和恢复；必要时使用错误汇总与焦点定位 |
| 上下文与恢复 | 返回、取消、刷新、重试的结果明确，保留约定的筛选/分页/草稿 | 实际执行完整路径；涉及未保存变更或不可逆操作时使用符合后果的保护 |
| 数据与权限状态 | 按场景区分加载、空数据、无匹配、错误、只读、无权限和成功 | 构造相关状态；错误不能显示成空数据，原型成功不能冒充真实保存 |
| 可访问与适配 | 标签、键盘、焦点、非颜色线索可用，动效尊重减少动画设置 | 手动验证关键操作；用可用工具检查对比度等问题，自动扫描不代替交互验证 |
| 内容边界 | 长文本、不同数据量和目标视口仍可理解、可操作 | 检查溢出、滚动、弹层和必要表格横向滚动；不以隐藏业务关键列解决适配 |

## 设计流程按范围裁剪

| 任务 | 工作方式 | 确认边界 |
| --- | --- | --- |
| 既有模式内的小调整、明确 UI bug | 读取基线，明确预期，直接修改并验证 | 不为了设计步骤额外停顿；有重要语义冲突时才确认 |
| 新页面或关键交互变化 | 任务与状态说明 → 布局/交互草案 → 可操作浏览器原型 → 验证与确认 → 正式实现 | 未确认的新设计先交付可审阅原型；已有明确且适用的设计确认不重复索取 |
| 新产品、导航或整体视觉变化 | 先明确核心任务与结构，再做代表性页面和候选基线 | 关键结构及代表性原型确认后再推广；确认不得扩展为发布或真实业务写入授权 |

需求与设计相互校验。设计阶段明确任务、信息、主要动作、页面状态、已知业务限制及待确认事项；已有 PRD 直接引用，不重新编造业务规则。仅有配色变化不算不同方案；只有存在实质取舍时才提供多个布局方案。

设计任务使用 `kit-ui-design`；实现后或单独验收使用 `kit-ui-review`。持久化记录优先使用业务工程既有设计记录；需要时参考 `templates/ui-design.md`。小任务可在对话记录，不要求完整模板。

## 浏览器原型与交付

- 沿用项目框架、组件和 Tailwind；新工程遵循 tooling。原型放入明确的隔离目录、入口或现有预览环境，不擅自安装设计平台、增加生产路由或替换构建链。
- 用有类型的合成 fixture 表达正常、边界和失败状态，原型标明演示用途；mock 与真实数据访问隔离，不把样例 ID、固定数字或假成功写成生产业务规则。原型授权不包含真实审批、通知、删除或发布。
- 原型应能演示核心操作及相关异常恢复，不能只有默认态截图。复用原型代码进入正式实现前，重新检查类型、状态分层、契约、注释和测试，替换演示数据入口；不因“已经确认外观”跳过工程验收。
- 验收记录路由/入口、基线版本或日期、视口、数据状态、操作及预期/实际结果、截图或检查报告。缺浏览器时可交付草案并标明未验证，不能声称原型可用或交互通过。
- Agent 负责执行可用检查、修正范围内问题、报告缺口；用户负责重要业务和设计选择，不让用户替代重复测试。机械检查适合类型、部分样式与可访问性问题；信息层级、任务效率、视觉一致性必须结合实际页面判断。

验收至少回答：是否符合业务任务、是否沿用适用基线、相关状态是否完整、核心路径是否实际验证。自查不是独立审查，未运行的模型行为评估不能标为通过。规范调整后通过真实任务持续校准，而不是宣称文件存在即可保证质量。
