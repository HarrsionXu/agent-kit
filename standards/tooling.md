# 工程工具链与新工程默认选型

适用 JavaScript/TypeScript 工程的初始化、依赖管理、构建和 CI；其他语言沿用对应生态，不强加 Node 工具链。2026-09-21 用户要求确定新工程的架构级标准，并明确确认新工程默认 pnpm、存量工程不迁移。

## 先判断新工程还是存量工程

- 新工程：尚无既定工具链的独立项目。按下列默认值落地，记录实际版本与选择依据，不把选型一直留作“按需决定”。
- 存量工程：已有 package.json、锁文件、构建配置、CI 或明确团队约定。保留原有包管理器、构建工具、框架、运行时和仓库组织；接入 Kit 不构成迁移授权。
- 在现有仓库新增页面、模块、包或 workspace 子应用，默认属于存量工程，继承根工具链；不能以“新功能”为由另引入 pnpm、Vite 或第二套锁文件。
- 优先对照项目规则、packageManager、锁文件、CI 和实际脚本确认事实。相互矛盾或存在多套遗留锁文件时先查明用途，不能擅自删文件或换工具来消除冲突。

## 新工程默认矩阵

| 决策项 | 默认标准 | 例外或边界 |
| --- | --- | --- |
| 包管理器 | pnpm；固定明确版本 | 用户指定、部署平台或依赖存在已核实的兼容限制时记录例外，不因个人偏好另选 npm/Yarn/Bun |
| JavaScript 运行时 | Node.js；初始化时优先选择与框架兼容、仍在 Active LTS 的版本线 | 平台限制时可选择仍受支持的 Maintenance LTS；不默认使用 Current、预发布或已停止支持的版本 |
| 业务代码 | TypeScript，启用 strict，并采用框架要求的编译/模板检查 | 配置文件按工具支持格式；原生模块或第三方契约的特殊要求需记录原因 |
| Vue/React 客户端单页应用（SPA） | Vite，使用对应框架的官方模板/插件与 TypeScript | 先确认是客户端应用；不将 SPA 默认值用于 SSR、移动原生或其他宿主 |
| Angular 应用 | Angular CLI 的官方 application builder，通过项目脚本执行 ng build/ng serve | Nx 工程通过已有 target；不能因开发服务器内部使用 Vite 就改为直接 vite build |
| SSR/SSG/全栈 Web 应用 | 所选框架的官方构建、路由与部署链 | 渲染需求和部署目标先明确，不为了统一 Vite 绕开框架；也不无依据为普通工作台引入服务端渲染 |
| Node 后端/CLI/公共库 | 优先所选框架的官方构建；无框架的 TS 工具或库默认使用 tsc | 只有分发、体积或运行环境需要打包时才另选 bundler，不能给所有 Node 工程套前端构建链 |
| 仓库组织 | 单应用默认单项目；多个紧密协作的包使用 pnpm workspace | 有任务图、缓存或大规模协作需求时再采用 Nx 等编排工具，不为单页应用预装整套 monorepo 平台 |
| 代码质量 | ESLint 与 Prettier，采用框架适配配置；职责分别为代码检查与格式化 | 避免重复冲突规则；已有工具链沿用，不能因接入 Kit 换 lint/格式化工具 |

以上是本 Kit 的工程默认决定，不代表官方要求所有项目采用同一工具。前端框架、组件库、状态库、数据库、部署平台及是否微前端仍由业务目标和项目约束决定，不因默认矩阵擅自添加。

## 版本、依赖与锁文件

1. 新工程在 package.json 的 packageManager 中固定包管理器的完整版本；Node 使用项目认可的单一版本文件（如 .node-version 或 .nvmrc）固定开发/CI 版本，并用 engines 声明支持范围。开发、CI、容器和部署环境需一致或有明确兼容矩阵，不能依赖本机全局工具“恰好可用”。
2. 初始化时查询官方兼容要求，核对 Node、框架、TypeScript、构建器和插件组合，记录核对日期及实际版本。标准不永久写死某个“最新版本”；一旦工程初始化，后续运行按已锁定版本，不在每次执行时重新解析 latest。升级作为显式变更验证。
3. 每个独立安装根只维护一种包管理器和对应锁文件；pnpm workspace 默认使用根 pnpm-lock.yaml。真正独立的嵌套工程需声明安装边界，不能简单按“一个 Git 仓库只能有一个锁文件”误删文件。
4. 锁文件必须提交。新增/升级依赖时同步更新 manifest 和锁文件并审查差异；不能为修安装问题删除锁文件、绕过 peer 约束或无依据开启全局 hoist。仅使用项目直接声明的依赖，不能依赖偶然提升的传递依赖。
5. 新 pnpm 工程在 CI 使用 pnpm install --frozen-lockfile；存量 npm 工程使用 npm ci，Yarn 等使用对应版本的不可变安装方式。锁文件不一致必须定位原因，不能由 CI 自动改锁文件后继续发布。
6. 包管理器安装方式也需固定在项目文档/CI 中并输出版本验证，不假设每个 Node 环境都自带 Corepack。私有 registry、代理和认证由项目配置，凭据不进入源码。

## 构建与命令边界

- 在 package.json 中提供稳定的项目命令入口，开发者、Agent 与 CI 使用同一脚本。默认约定 dev（本地开发）、build（生产构建）、typecheck、lint、format:check、test 和 check（汇总本地质量检查）；浏览器测试按需要增加 test:e2e。
- 命令必须绑定真实工具和可观察检查。没有测试或某项确实不适用时记录缺口/原因，不创建 echo 成功或忽略错误的占位脚本。框架把类型检查并入构建时，明确对应映射，避免重复执行完整构建。
- check 不包含部署、数据库迁移、真实审批或通知。完整交付需有类型/模板、代码检查、相关测试和生产构建证据；检查如何组合由项目配置，不能因为命名为 check 就推定包含所有项。
- Vite 的转译/打包不替代 TypeScript 类型检查；Angular 的 ng build 与 Vite 的 vite build 是不同入口。开发启动、HMR 正常不能替代生产构建和产物验证。
- 明确资源 base path、环境变量注入、输出目录、浏览器目标及 source map 策略。前端打包进产物的环境变量可被用户获取，不能放秘密；部署子路径时核验静态资源和深链刷新。
- monorepo 根脚本负责调度，子包脚本负责自身构建；公共契约与业务库有明确依赖方向。微前端组合必须验证实际插件/版本和生产产物互操作性，不能仅凭同名 Federation 或 Vite 支持就认定可组合。

## 存量工程如何参考

沿用 npm 的工程继续 npm，沿用 Webpack、Angular CLI、Nx 或既有 SSR 构建链的工程继续原工具链；Kit 本身也继续使用现有 npm 命令。普通改动使用现有的版本、锁文件和 CI，不顺带升级依赖或重命名脚本。

可按当前授权范围参考并逐步完善：版本记录、锁文件与可重复安装、依赖声明、脚本含义、类型与构建分离、生产产物验收及证据。工具链缺口先说明影响；补齐配置或检查需属于当前任务，不能借“参考规范”扩大为全库整改。迁移框架、包管理器、模块系统或构建器需单独提出依据、兼容性与回滚方案，获明确授权后再实施。

## 决策记录与验收

在项目事实文档中记录工程类别、渲染形态、工具及版本、安装根/锁文件、开发和 CI 命令、部署产物、例外原因与复查条件；沿用存量工具不需要另写一份迁移申请。Kit 的 project.json 只填写其已支持字段，其他事实写到项目文档，不能添加工具不会读取的配置来假装生效。

新工程至少验证：隔离环境中的锁定安装、类型/模板检查、代码质量检查、相关测试、生产构建，以及与项目类型对应的启动/产物冒烟检查。存量任务运行与变更相关的现有检查并报告已知缺口；不能只证明 Kit 分发成功就声称业务工具链已验证。
