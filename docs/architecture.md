# 架构与边界

## 决策

标准集中维护，经过审核的副本固定在业务仓库中。Agent 在业务仓库工作，不需要跨目录寻找最新规则，也不依赖联网读取远程主分支。

| 层次 | 职责 | 不负责 |
| --- | --- | --- |
| standards | 公共约束、框架差异、交付要求 | 固定所有项目技术版本 |
| .agents/skills | 按任务触发的操作流程 | 自动加载所有规则、代替项目事实 |
| catalog.json | profile 到规则/Skills 的映射 | 模型调度 |
| CLI | 安装、冲突检查、完整性检查、本地验证 | 权限沙箱、CI 服务、业务部署 |
| 业务项目配置 | 技术栈、命令、设计基线、例外 | 修改中央发布包 |

业务仓库安装后保留版本、摘要与本地配置，升级需显式执行。Skill 内容遵守项目内 AGENTS 和平台指令；README 链接本身不会让其他工程自动读取标准。

## 目录与职责

- `standards/`：公共规范和 profile；tooling 定义新工程工具链默认值与存量兼容边界，Angular/Vue/React 各自定义 HTTP、路由、状态与验证要求。
- `.agents/skills/`：独立、按需读取的任务方法；安装时仅复制选中的技能。
- `src/kit.mjs`：分发及验证逻辑，`bin/agent-kit.mjs` 是薄入口。
- `templates/`：项目事实、验收/交付记录。
- `tests/`：隔离临时项目中测试，不调用业务接口。
- `evals/`：Agent 行为评估用例，区别于 CLI 单测。

## 分发协议

目标项目的 `AGENTS.md` 只追加一个受管理区块，不替换原文。规则与工具放入 `.agent-kit/`，技能放入 `.agents/skills/`。`project.json` 和 `project.md` 归项目所有，升级不覆盖。

预检全部受管理文件与路径后才写入；检测到人工改动、同名非托管文件、符号链接、旧版本规则冲突即拒绝。变更前保存受影响文件的备份。文件替换采用临时文件 + rename；**整批安装不具备跨文件原子性**，断电/磁盘错误时从备份恢复，不承诺无人值守事务升级。不要并发安装到同一目标。

首版不支持移除 profile 或自动卸载，避免自动删除手写补充内容。升级不得降版本，相同版本不得换内容。项目可以显式增补 profile，应用目录的适用范围由 project.json 声明。

## Harness 的含义

工作闭环是：读取规则和项目事实 → 明确验收 → 必要设计 → 实现与检查 → 按任务核验行为/视觉 → 修正 → 交付证据。这里提供规则分发和检查入口，Agent/人仍负责执行判断、浏览器验收和必要的审批；纯文档任务不要求无关的浏览器测试。

本项目不是新的 LLM 平台，也不把 product-analyst → architect → engineer → qa-devops 固定为每次必须逐个人工放行。低风险任务一个闭环完成；需求和架构决策复杂时才拆步骤。更高优先级指令与业务仓库的审批边界仍有效。

角色职责、风险分级、暂停条件、任务记录及完成标准统一维护在 [workflow](../standards/workflow.md)。它约束 Agent 的工作方式，不是运行时状态机；行为是否遵从需按 evals 方法实际观察，不能由 CLI 校验文档存在就推定通过。
